# Refinar una HU de AVAO

1. Lee la HU vigente en `docs/product/Backlog.md`, la guía `docs/workflow/GuiaBacklogKanban.md` y solo los documentos de dominio pertinentes. Si la HU ya está en GitHub Projects, comprueba allí su contenido actual antes de proponer cambios. No dupliques el tablero en Markdown.
2. Identifica papel real, necesidad observable, beneficio y resultado comprobable. Redacta preferentemente **«Como [papel], necesito [capacidad], para [beneficio]»**. «Quiero» puede expresar una capacidad opcional, pero **ningún verbo determina por sí solo el MVP o la prioridad**: anota esa decisión por separado y confirma con el usuario.
3. Distingue **hecho confirmado**, **propuesta**, **supuesto** y **pregunta abierta**. El usuario es la fuente principal sobre la vidriería. La investigación externa sugiere posibilidades, no establece reglas del taller. No inventes fracciones, cálculos, redondeos, excepciones, identificadores ni estados.
4. Busca una unidad pequeña de valor que funcione de extremo a extremo. Separa comportamientos con beneficio y aceptación propios; une pasos que, aislados, no sirvan al usuario. Una HU no es un paquete de frontend, backend, base de datos ni tareas técnicas. Las dependencias entre HU son aceptables si son explícitas y permiten entregas utilizables. Aplica INVEST como conversación y la precisión/verificabilidad de ISO/IEC/IEEE 29148 de forma proporcional, sin crear una especificación extensa.
5. Antes de formalizar reglas inciertas, pregunta al usuario con un ejemplo concreto. Para una HU próxima, propón criterios suficientes para caminos esenciales y límites conocidos; no impongas un número fijo. Separa subtareas de implementación de esos criterios. Estima y prioriza según el proceso vigente cuando la HU se acerque al trabajo; el usuario decide valor para MVP.
6. Entrega propuesta breve: HU o división sugerida, valor de cada parte, dependencias, criterios comprobables, fuera de alcance y preguntas pendientes. No anuncies prioridad definitiva mientras una decisión de dominio o MVP esté abierta.

Mantén separado el cálculo básico de cortes de una futura optimización de material 1D/2D. Al dividir una HU, conserva su intención y sus enlaces sin convertir una decisión pendiente en regla confirmada.
